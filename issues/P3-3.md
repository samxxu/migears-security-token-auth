# P3-3 — `deviceId` is stored verbatim, CR and LF included. Harmless here …

## Finding / 问题

- EN: `deviceId` is stored verbatim, CR and LF included. Harmless here because it never becomes a header, but a downstream consumer that copies it into a header or a log inherits the risk. Handled in the working tree by a design-doc note at `docs/token-auth-design/token-auth-design.html:965-969`.
- 中文: `deviceId` 原样存储，含 CR 与 LF。此处无害，因为它从不成为报文头；但下游若把它放进头部或日志就会继承该风险。工作树中已处理：设计文档说明在 `docs/token-auth-design/token-auth-design.html:965-969`。

- 2026-10-01 · `owner — migears-security-token-auth` · `fixed` —
  - **fixed** — the boundary the finding records is now stated, in both halves, at
    `docs/token-auth-design/token-auth-design.html:965-969`: `deviceId` is recorded exactly as passed,
    control characters included; the module neither normalises nor rejects it; it only ever lands in
    the record's value and never in a cache key; a caller that echoes or logs it must validate or
    sanitise it like any other caller-supplied string.
  - Probe (temp dir outside the repo): `issue($user, deviceId: "a\r\nb\t\x00c")` stores that 7-byte
    string verbatim in the access record's `device_id`, and a rotation carries the same value onto the
    successor refresh record. It never reaches `TokenAuth::recordKey()` / `familyKey()` / `userKey()`,
    which hash only the token, the family id and the user id.
  - No code change in this pass: rejecting or normalising a caller-supplied identifier would be a
    behaviour change on a public parameter, and the module's documented position is to record it as
    given and let the caller sanitise whatever it echoes or logs.
